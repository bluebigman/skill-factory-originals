## 三、标准流程：从输入到输出

### 3.1 前置条件

- 输入必须是一个**需求描述**，而非具体软件名称
- 需求描述应包含**类别词**（如"博客"、"网盘"、"CRM"）
- 可选：附加约束条件（技术栈、部署方式、社区活跃度）

### 3.2 执行步骤

**步骤 1：解析输入**

将输入拆解为「类别词 + 约束条件」：

| 输入示例 | 类别词 | 约束条件 |
|----------|--------|----------|
| "用 Go 写的自托管笔记软件" | 笔记 | 语言: Go |
| "支持 Docker 的轻量级博客" | 博客 | 部署: Docker；特性: 轻量级 |
| "有活跃社区的项目管理工具" | 项目管理 | 社区: 活跃 |

**步骤 2：匹配内置知识库**

在知识库中查找与类别词匹配的软件条目。知识库覆盖以下分类（非穷举）：

| 分类 | 示例软件 |
|------|----------|
| 博客/内容管理 | Ghost, WordPress, Hexo |
| 文件同步/共享 | Nextcloud, Seafile, Syncthing |
| 笔记/知识库 | Joplin, Trilium, Outline |
| 项目管理 | Redmine, Taiga, OpenProject |
| CRM/客户管理 | SuiteCRM, EspoCRM, Odoo |
| 监控/运维 | Grafana, Prometheus, Zabbix |
| 通讯/协作 | Mattermost, Rocket.Chat, Zulip |
| 数据库管理 | Adminer, phpMyAdmin, DBeaver |

**步骤 3：应用约束条件过滤**

对匹配结果逐一检查约束条件，剔除不满足的条目。约束条件优先级从高到低：

1. **许可证**：必须为开源许可证（MIT、Apache-2.0、GPL 等）
2. **部署方式**：支持 Docker、裸机、Kubernetes 等
3. **技术栈**：编程语言、框架
4. **社区活跃度**：Star 数、最近提交时间

**步骤 4：生成结构化输出**

输出格式如下：

```markdown
| 软件名称 | 分类 | 技术栈 | 许可证 | Star 数 | 部署方式 | 备注 |
|----------|------|--------|--------|---------|----------|------|
| Ghost | 博客 | Node.js | MIT | 45k+ | Docker/裸机 | 专业级发布平台 |
| WordPress | 博客 | PHP | GPL-2.0 | 18k+ | Docker/裸机 | 生态最丰富 |
```

**步骤 5：附加建议**

在表格下方，附上 2-3 条选型建议，例如：

> 建议：若追求轻量级，优先考虑 Ghost；若需要插件生态，WordPress 更合适。建议进一步查看官方文档确认版本兼容性。

### 3.3 输出规范

- 表格必须包含：软件名称、分类、技术栈、许可证、Star 数、部署方式
- 候选数量控制在 3-8 个，过多时按 Star 数降序排列
- 每条候选附一行备注，说明核心优势或适用场景
- 输出末尾必须包含"建议"部分，给出选型方向
