# aider — 终端内 AI 结对编程助手

## 一、能力边界（一页纸速查卡）

### 1.1 能做清单

| 能力项 | 说明 | 典型场景 |
|--------|------|----------|
| 多文件协同编辑 | 同时读取并修改多个源文件，保持跨文件一致性 | 重构接口时同步更新调用方 |
| 自动 Git 提交 | 每次修改完成后自动创建提交，附带结构化提交信息 | 连续迭代时无需手动 commit |
| 差异审查 | 展示每次修改的 diff，支持逐行确认 | 提交前快速核对改动范围 |
| 变更回滚 | 通过提交历史回退到任意先前版本 | 修改引入回归时快速恢复 |
| 终端交互 | 纯命令行界面，无需离开终端 | SSH 远程开发、无 GUI 环境 |
| 上下文感知 | 自动读取仓库结构、最近提交、相关文件内容 | 新加入项目时快速理解代码 |

### 1.2 不能做清单

| 限制项 | 说明 |
|--------|------|
| 不执行代码 | 只生成和修改代码，不负责运行、编译、测试验证 |
| 不处理部署 | 不涉及 CI/CD 流水线、服务器部署、环境配置 |
| 不替代人工审查 | 自动提交不意味着免审查，关键改动仍需人工确认 |
| 不支持二进制文件 | 仅处理文本文件，图片、压缩包等二进制内容无法编辑 |
| 不保证编译通过 | 修改后的代码可能存在语法错误或逻辑缺陷，需自行验证 |

### 1.3 适用对象

- **适合**：个人开发者、小团队、开源维护者，习惯命令行工作流，希望减少重复性 Git 操作。
- **不适合**：需要严格代码审查流程的企业团队、非技术背景用户、对 AI 生成代码持谨慎态度的项目。

## 三、标准流程

### 3.1 前置条件

| 条件 | 检查项 | 不满足时的处理 |
|------|--------|----------------|
| Git 仓库 | 当前目录已 `git init` | 提示先初始化仓库 |
| 文件存在 | 指定的文件路径有效 | 报错并列出可用文件 |
| 网络连接 | 可访问 AI 服务端点 | 提示检查网络或代理设置 |
| 权限 | 对目标文件有读写权限 | 提示使用 sudo 或调整权限 |

### 3.2 执行步骤

**Step 1：环境初始化**

```bash
# 检查 Git 状态
git status --short

# 确认当前分支
git branch --show-current
```

**Step 2：加载上下文**

- 读取仓库根目录下的 `.aider.conf.yml`（若存在）
- 扫描最近 10 条提交记录，了解项目演进
- 加载用户指定的文件内容到工作区

**Step 3：接收指令**

- 交互模式下等待用户输入自然语言指令
- 命令行模式下解析参数中的文件列表和指令

**Step 4：生成修改**

- 分析指令意图，定位相关代码段
- 生成修改方案，展示拟变更的 diff
- 等待用户确认（`y` 接受 / `n` 拒绝 / `e` 编辑）

**Step 5：自动提交**

```bash
# 确认后自动执行
git add -A
git commit -m "feat: 描述性提交信息"
```

**Step 6：输出结果**

- 展示提交哈希、变更文件数、插入/删除行数
- 提供下一步建议（如"继续修改其他文件"或"运行测试验证"）

### 3.3 输出规范

| 输出项 | 格式 | 示例 |
|--------|------|------|
| 修改摘要 | 文件路径 + 变更类型 | `src/main.py: 修改函数 calculate_total()` |
| Diff 展示 | 统一 diff 格式 | `+ 新增行` / `- 删除行` |
| 提交信息 | 遵循 Conventional Commits | `fix: 修复空指针异常` |

### 6.1 常见坑与反模式对照

| 常见坑 | 反模式（错误做法） | 正模式（推荐做法） |
|--------|-------------------|-------------------|
| 自动提交后才发现改错 | 直接回退到上一个提交，丢失所有中间修改 | 先查看提交历史，定位到具体错误提交，使用 `git revert` 精准回退 |
| 多文件修改时遗漏关联文件 | 只修改了主文件，忽略调用方 | 修改前先搜索所有引用该函数/变量的文件 |
| 提交信息过于笼统 | 使用 "update" 或 "fix" 作为提交信息 | 遵循 Conventional Commits 格式，写明修改内容和原因 |
| 依赖 AI 生成代码而不审查 | 直接接受所有 AI 建议的修改 | 逐行审查 diff，理解每处变更的目的 |
| 在错误分支上操作 | 未确认当前分支就进行修改 | 操作前先执行 `git branch --show-current` 确认分支 |
