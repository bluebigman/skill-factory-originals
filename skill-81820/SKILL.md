## 三、标准流程：从输入到输出

### 3.1 前置条件

| 条件项 | 要求 |
|--------|------|
| 输入格式 | 纯文本（.txt）、Markdown（.md）、OCR 文本（粘贴为纯文本） |
| 输入大小 | 单次处理不超过 50,000 字符（约 8,000 汉字） |
| 环境要求 | 本地运行，无需联网；若使用 CLI，需 Python 3.8+ |

### 3.2 执行步骤（分步编号）

**Step 1：内容接收与预检**

- 接收用户提供的原始笔记内容。
- 检查内容是否为空、是否超过长度限制、是否包含明显乱码。
- 若内容为空，输出提示："未检测到输入内容，请提供需要整理的笔记。"

**Step 2：笔记识别与解析**

- 扫描文本，识别以下元素：
  - 标题（以 `#` 开头或独立成行的短句）
  - 列表项（以 `-`、`*`、`1.` 开头）
  - 关键实体（人名、日期、项目名、数字指标）
- 生成一个临时解析树，记录元素之间的层级关系。

**Step 3：结构整理与重构**

- 根据解析树，将内容重排为以下标准结构：
  ```markdown
  # 笔记主题（自动提取或用户指定）
  
  ## 背景与上下文
  （原文中描述背景的段落）
  
  ## 核心内容
  ### 子主题 1
  （相关列表或段落）
  ### 子主题 2
  （相关列表或段落）
  
  ## 行动项 / 待办
  - [ ] 事项 1
  - [ ] 事项 2
  
  ## 参考与备注
  （原文中的链接、引用、补充说明）
  ```
- 若原文无明确主题，使用第一个标题或前 20 字作为主题，并标注 `[自动提取]`。

**Step 4：内容生成（可选）**

- 若用户需要摘要，生成 100-200 字摘要，置于文档开头 `> 摘要：...`。
- 若用户需要待办清单，从原文中提取含"需""要""必须""待办"等词的句子，转为 `- [ ]` 格式。

**Step 5：质量校验与输出**

- 执行校验规则（见 3.3 输出规范）。
- 输出最终 Markdown 文件，文件名为 `整理结果_YYYYMMDD_HHMMSS.md`。
- 同时输出一份校验报告（若发现问题），格式如下：
  ```
  校验报告：
  - 缺失标题：无
  - 未解析列表：2 处（第 15 行、第 32 行）
  - 建议人工复核：OCR 识别段落（第 40-45 行）
  ```

### 3.3 输出规范

| 输出项 | 规范要求 |
|--------|----------|
| 文件格式 | 标准 Markdown（.md），UTF-8 编码 |
| 标题层级 | 最多使用三级标题（`#`、`##`、`###`），禁止四级以上 |
| 列表格式 | 无序列表用 `-`，有序列表用 `1.`，待办用 `- [ ]` |
| 引用格式 | 原文引用使用 `>` 符号，并注明来源（如 `> 原文第 3 段`） |
| 占位符 | 信息不足时使用 `[需核实:字段名]` 占位，如 `[需核实:会议日期]` |

## 四、置信度门控：不编造原则

当遇到以下情况时，必须使用占位符，禁止猜测或编造：

| 场景 | 处理方式 | 示例 |
|------|----------|------|
| 原文中未提及日期 | 输出 `[需核实:日期]` | 行动项截止日期未知 → `- [ ] 完成报告 [需核实:截止日期]` |
| OCR 识别模糊的专有名词 | 输出 `[需核实:专有名词]` | 人名识别不清 → `[需核实:发言人姓名]` 提出该方案 |
| 原文存在矛盾信息 | 保留原文两处内容，并标注 | `原文第 2 段提到 A，第 5 段提到 B，[需核实:以哪个为准]` |

## 六、FAQ 反模式：常见坑与对照

| 常见坑（反模式） | 错误做法 | 正确做法 |
|------------------|----------|----------|
| **过度整理** | 将原文中所有句子都强行归类到某个子标题下，导致结构臃肿 | 保留原文中无法归类的段落为"备注"，不强行分类 |
| **丢失原文信息** | 整理时删除了看似"不重要"的句子，导致信息缺失 | 所有原文内容必须保留在整理稿中，仅调整位置，不删除 |
| **忽略上下文** | 将列表项从上下文中剥离，导致语义不清 | 列表项前保留其所属段落的首句作为引导 |
| **格式混乱** | 混用 `-`、`*`、`+` 作为列表符号 | 统一使用 `-` 作为无序列表符号 |
| **虚假精确** | 对不确定的信息强行填写猜测值 | 使用 `[需核实:字段]` 占位，并提示用户补充 |
