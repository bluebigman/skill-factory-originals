# signal-wiki 技能文档

## 一、能力边界速查卡

### 1.1 能做与不能做

| 维度 | 能做 | 不能做 |
|------|------|--------|
| 输入处理 | 接受用户提供的文本、文件路径、URL 链接 | 不接受二进制文件（图片/音频/视频）的直接解析 |
| 信息提取 | 识别时间、地点、人物、事件、数据指标等关键要素 | 不进行主观价值判断（如"好/坏"） |
| 结构化输出 | 生成 Markdown 表格、JSON 对象、条目列表 | 不生成 PDF、Word 等非纯文本格式 |
| 批量操作 | 支持多文件顺序处理，每次最多 20 个条目 | 不支持并行异步处理 |
| 自定义格式 | 允许用户指定字段顺序和输出模板 | 不支持编程式自定义（如写脚本） |
| 置信度标注 | 对不确定信息标注 `[需核实:字段名]` | 不编造缺失信息 |

### 1.2 适用对象

- **内容创作者**：需要将零散笔记整理为结构化知识卡片
- **研究人员**：需要从多来源资料中提取关键信息
- **普通用户**：希望快速将网页内容转为可复用的条目

### 1.3 不适用场景

- 需要深度语义理解的文学分析
- 需要实时数据抓取的动态监控
- 需要法律/医疗等专业领域权威结论

## 三、标准处理流程

### 3.1 前置条件

| 条件项 | 要求 |
|--------|------|
| 输入文件 | 文本格式（.txt/.md/.csv），编码 UTF-8 |
| 文件命名 | 建议格式：`序号_名称.txt`（如 `01_会议纪要.txt`） |
| 文件位置 | 与工作目录同一层级，或提供完整路径 |
| 单次输入量 | 不超过 20 个条目或 5000 字 |

### 3.2 执行步骤

**步骤 1：输入解析**

- 读取用户提供的文本/文件/URL
- 识别内容类型（叙述型/数据型/混合型）

**步骤 2：关键信息提取**

按以下优先级提取字段：

| 优先级 | 字段 | 说明 |
|--------|------|------|
| P0 | 标题 | 内容的核心主题 |
| P0 | 日期 | 事件发生或内容创建时间 |
| P1 | 来源 | 原始出处（URL/文件名/作者） |
| P1 | 关键数据 | 数字、百分比、统计值 |
| P2 | 摘要 | 2-3 句话概括核心内容 |
| P2 | 标签 | 3-5 个关键词分类 |

**步骤 3：置信度评估**

- 信息完整且明确 → 正常输出
- 信息缺失或模糊 → 标注 `[需核实:字段名]`
- 多来源冲突 → 保留主要来源，标注冲突提示

**步骤 4：结果生成**

- 默认输出 Markdown 表格格式
- 按用户自定义模板输出（如仅标题+日期）

**步骤 5：自查校验**

- 检查字段完整性（P0 字段必须齐全）
- 检查格式正确性（表格对齐、无多余空格）
- 检查置信度标注是否遗漏

### 3.3 输出规范

**默认输出模板：**

```markdown
| 字段 | 内容 |
|------|------|
| 标题 | （提取的标题） |
| 日期 | （提取的日期，格式 YYYY-MM-DD） |
| 来源 | （URL/文件名） |
| 关键数据 | （如有，列出；无则填"无"） |
| 摘要 | （2-3 句概括） |
| 标签 | （逗号分隔的关键词） |
| 置信度 | 高/中/低（附说明） |
```

**批量输出格式：**

```markdown
## 处理结果汇总

共处理 N 个条目，成功 M 个，需核实 K 个。

### 条目列表
（按上述模板逐条列出）

### 需核实项
（列出所有标注 [需核实] 的字段及原因）
```

## 四、置信度门控机制

### 4.1 置信度等级定义

| 等级 | 判定标准 | 输出样式 |
|------|---------|---------|
| 高 | 信息直接来自原文，无歧义 | 正常输出 |
| 中 | 信息经过推断，但逻辑清晰 | 正常输出，附注"推断" |
| 低 | 信息模糊或来源不可靠 | 标注 `[需核实:字段名]` |

### 4.2 需核实场景示例

| 场景 | 处理方式 |
|------|---------|
| 日期格式不完整（只有年份） | `[需核实:日期]`，保留已有信息 |
| 数据单位不明确 | `[需核实:单位]`，保留数值 |
| 多来源信息冲突 | 保留主要来源，标注 `[需核实:冲突项]` |
| 内容超出理解范围 | `[需核实:内容]`，不强行解读 |

### 4.3 禁止行为

- 不猜测缺失的日期（如默认填当天）
- 不推断未提及的人物关系
- 不补充原文没有的数据

## 六、FAQ 与反模式对照

### 6.1 常见坑

**坑 1：过度解读**

- ❌ 反模式：原文只说"增长"，输出写"大幅增长 50%"
- ✅ 正确做法：输出"增长"，标注 `[需核实:增长率]`

**坑 2：忽略来源**

- ❌ 反模式：整理内容时不记录 URL 或文件名
- ✅ 正确做法：每个条目必须包含来源字段

**坑 3：格式混乱**

- ❌ 反模式：日期一会儿用"2024.1.1"，一会儿用"2024-01-01"
- ✅ 正确做法：统一使用 `YYYY-MM-DD` 格式

**坑 4：批量处理不校验**

- ❌ 反模式：批量处理后直接交付，不抽查结果
- ✅ 正确做法：至少抽查 20% 的条目核对准确性

**坑 5：编造缺失信息**

- ❌ 反模式：日期缺失时填"未知"或猜测日期
- ✅ 正确做法：标注 `[需核实:日期]`，保留空白

### 6.2 反模式对照表

| 反模式 | 问题 | 正确替代 |
|--------|------|---------|
| 强行总结 | 丢失细节 | 保留原文关键句 |
| 只输出结论 | 无法追溯 | 附来源和上下文 |
| 忽略异常 | 错误累积 | 标注所有不确定项 |
| 一次处理过多 | 质量下降 | 分批处理，每批不超过 20 条 |
