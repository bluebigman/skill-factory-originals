## 三、标准处理流程（前置条件 → 执行步骤 → 输出规范）

### 前置条件（必须满足）

1. 用户需提供至少一种数据源：评价文本（≥10 条）、菜单文件、门店基本信息（名称、地址、品类）。
2. 若为批量处理，需将所有文件置于同一文件夹内，并确保文件名包含门店标识（如 `store_a_reviews.csv`）。
3. 所有文本需为 UTF-8 编码，避免乱码导致解析失败。

### 执行步骤（分步编号）

**步骤 1：输入接收与格式识别**

- 检查输入类型：若为命令行参数，解析 `--input` 指向的文件路径；若为交互输入，直接读取粘贴文本。
- 格式判定规则：
  - 以 `{` 开头 → JSON 格式，尝试解析为 `{reviews: [], menu: {}, store_info: {}}`。
  - 以 `#` 或 `|` 开头 → Markdown 表格，按行读取。
  - 包含 `http://` 或 `https://` → 提示用户手动复制页面文本（本 Skill 不发起网络请求）。
  - 其他 → 视为纯文本，按段落切分。

**步骤 2：数据清洗与结构化**

- 评价文本：去除表情符号、@提及、超链接；按句号/感叹号分割为独立观点单元。
- 菜单文件：若为 PDF，需用户先行转换为文本或 Excel；提取菜品名、价格、分类（如热菜/凉菜/主食）。
- 门店信息：提取关键字段（名称、地址、营业时间、人均消费、菜系标签）。

**步骤 3：核心分析逻辑**

- **评价分析**：构建情感词典（正面/负面/中性），计算每条评价的情感得分（范围 -1 到 1）。提取高频名词（如"服务""上菜速度""口味"）作为主题，统计各主题下的负面提及率。
- **菜单优化**：计算品类占比（如热菜占比 60% 是否合理）；识别价格带分布（低于 30 元、30-60 元、60 元以上）；标记疑似滞销品（价格高且无评价提及）。
- **本地搜索诊断**：检查门店名称是否包含品类关键词（如"老张川菜馆"优于"老张"）；地址描述是否含地标（如"近地铁 2 号线"）；类目选择是否与主营匹配。

**步骤 4：置信度评估**

- 每条输出结果附带 `confidence` 字段，取值范围 0.0-1.0。
- 置信度计算规则：
  - 评价分析：基于有效样本量。样本量 < 10 条 → 置信度 ≤ 0.4；10-30 条 → 0.5-0.7；> 30 条 → 0.8-1.0。
  - 菜单优化：基于菜单完整性。若缺少价格或分类信息 → 置信度 ≤ 0.5。
  - 本地搜索诊断：若门店信息缺失地址或品类 → 置信度 ≤ 0.3。

**步骤 5：输出生成（结构化 JSON）**

输出遵循以下统一 Schema：

```json
{
  "analysis_type": "review_analysis | menu_optimization | store_diagnosis | local_seo",
  "summary": "一段话总结核心发现",
  "details": [
    {
      "item": "具体分析项名称",
      "finding": "发现的问题或亮点",
      "evidence": "支撑该发现的原始数据引用（如评价原文片段）",
      "suggestion": "可操作建议",
      "confidence": 0.85
    }
  ],
  "action_priority": ["高优先级建议1", "中优先级建议2", "低优先级建议3"]
}
```

**步骤 6：建议提供**

- 每条建议需包含执行主体（谁来做）、时间范围（何时做）、预期效果（可衡量的指标，如"差评率降低 15%"——注意此为示例，不构成承诺）。

## 四、置信度门控与信息不足处理

当输入数据不足以支撑可靠结论时，本 Skill 将执行以下规则：

1. **缺失字段占位**：在输出的 `details[].finding` 中，使用 `[需核实:字段名]` 格式标注缺失信息。例如：`[需核实:门店地址]`。
2. **禁止编造**：绝不推测缺失的菜单价格、评价内容或门店营业状态。若用户未提供，则明确标注"未提供，无法分析"。
3. **降级处理**：若评价样本量 < 5 条，则跳过情感分析，仅输出"样本不足，建议收集更多评价后再分析"。
4. **冲突数据**：若同一门店在不同来源（如大众点评 vs 美团）的信息冲突，输出时同时列出两个来源的数据，并标注 `conflict: true`，建议用户核实。
