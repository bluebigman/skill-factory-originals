## 三、标准处理流程

### 3.1 前置条件

- 输入地址文本长度 ≥ 4 个字符
- 地址文本必须包含至少一个行政区划关键词（省/市/区/县/镇/街道）
- 输入编码为 UTF-8

### 3.2 执行步骤

**步骤 1：地址文本预处理**

- 去除首尾空白字符
- 统一全角/半角符号（将全角逗号、句号转为半角）
- 移除无关修饰词（如"大约""大概""靠近"等）

**步骤 2：行政区划匹配**

- 将地址文本与内置行政区划词典进行最长匹配
- 依次识别：省级 → 市级 → 区县级 → 乡镇/街道级
- 记录每个层级的匹配结果与匹配位置

**步骤 3：精细地址解析**

- 在区划匹配的基础上，尝试提取道路名、门牌号、楼栋号
- 若提取成功，尝试匹配道路级坐标库
- 若道路匹配失败，使用区划中心点坐标

**步骤 4：置信度计算与输出**

- 根据匹配层级与字段完整度计算置信度
- 按「置信度门控」规则决定输出结果或降级/拒绝

### 3.3 输出规范

成功解析时，输出 JSON 格式：

```json
{
  "status": "OK",
  "input": "北京市朝阳区建国路88号",
  "parsed": {
    "province": "北京市",
    "city": "北京市",
    "district": "朝阳区",
    "street": "建国路",
    "street_number": "88号"
  },
  "location": {
    "lat": 39.9087,
    "lng": 116.3975
  },
  "match_level": "precise",
  "confidence": 0.92
}
```

**字段说明：**

| 字段 | 类型 | 说明 |
|------|------|------|
| `status` | string | 处理结果状态，`OK` 或错误码 |
| `input` | string | 原始输入地址 |
| `parsed` | object | 结构化解析结果，未识别字段为 `null` |
| `location` | object | 坐标结果，`lat` 为纬度，`lng` 为经度 |
| `match_level` | string | 匹配级别，取值见下表 |
| `confidence` | number | 置信度，范围 0~1 |

**match_level 取值表：**

| 取值 | 含义 | 典型置信度范围 |
|------|------|----------------|
| `precise` | 精确到门牌号/楼栋 | 0.90 ~ 1.00 |
| `street` | 精确到道路 | 0.80 ~ 0.89 |
| `district` | 精确到区县 | 0.60 ~ 0.79 |
| `locality` | 精确到市级 | 0.40 ~ 0.59 |
| `administrative_area_level_1` | 精确到省级 | 0.20 ~ 0.39 |

## 四、置信度门控

### 4.1 降级策略

当解析结果无法达到精确级别时，按以下顺序降级：

1. **降级到市级**：当区县级匹配失败但市级匹配成功时，返回该市市政府所在地坐标，标注 `match_level: "locality"`
2. **降级到省级**：当市级匹配失败但省级匹配成功时，返回该省省会坐标，标注 `match_level: "administrative_area_level_1"`
3. **拒绝解析**：当省级匹配失败时，返回 `INCOMPLETE_ADDRESS` 错误，要求用户补充省/市信息

### 4.2 信息不足处理

当输入地址缺少必要字段时，输出占位符 `[需核实:字段名]`，不编造数据：

```json
{
  "status": "OK",
  "input": "朝阳区建国路88号",
  "parsed": {
    "province": "[需核实:省份]",
    "city": "[需核实:城市]",
    "district": "朝阳区",
    "street": "建国路",
    "street_number": "88号"
  },
  "location": {
    "lat": 39.9087,
    "lng": 116.3975
  },
  "match_level": "district",
  "confidence": 0.65
}
```

### 4.3 阈值参数参考

| 参数 | 默认值 | 说明 |
|------|--------|------|
| `precise_threshold` | 0.90 | 高于此值视为精确匹配 |
| `street_threshold` | 0.80 | 高于此值视为道路级匹配 |
| `district_threshold` | 0.60 | 高于此值视为区县级匹配 |
| `locality_threshold` | 0.40 | 高于此值视为市级匹配 |
| `min_confidence` | 0.20 | 低于此值拒绝输出坐标 |

## 六、FAQ 反模式

### 6.1 常见坑与反模式对照

| 反模式（错误做法） | 正确做法 |
|---------------------|----------|
| 直接传入用户原始输入，不做任何清洗 | 先去除表情符号、特殊字符、无关修饰词 |
| 将低置信度结果直接用于精确导航 | 根据 `match_level` 判断结果适用场景，市级坐标仅适合城市级分析 |
| 忽略 `INCOMPLETE_ADDRESS` 错误，反复重试同一地址 | 引导用户补充省/市信息，或使用默认省/市（需业务方确认） |
| 将 `district` 级别结果当作精确地址存储 | 在数据模型中增加 `match_level` 字段，区分精度 |
| 每次请求都调用外部 API，不做缓存 | 对高频地址建立本地缓存，减少重复计算 |

### 6.2 输入预处理建议

- **统一行政区划名称**：将"内蒙古"规范为"内蒙古自治区"，将"北京"规范为"北京市"

- **处理缩写**：将"国贸"展开为"建国门外大街"（需业务方维护缩写词典）
