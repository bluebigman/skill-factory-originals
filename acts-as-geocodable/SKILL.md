# 地址解析与地理编码技能（acts-as-geocodable）

## 一、能力边界：一页纸速查卡

本技能专注于**地址文本 → 结构化地理数据**的转换，不涉及地图渲染、路径规划或实时定位。

| 维度 | 能做 | 不能做 |
|------|------|--------|
| 输入处理 | 中文地址、英文地址、混合地址、模糊地址（如"北京市海淀区中关村"） | 非地址文本（如人名、商品名） |
| 输出内容 | 结构化地址组件、经纬度坐标、置信度评分、匹配级别 | 行政区划代码（需另行对接）、时区信息 |
| 解析能力 | 省/市/区/街道/门牌号/楼栋/单元/房间号逐级拆分 | 历史地名自动映射（如"北平"→"北京"） |
| 坐标精度 | 返回 WGS-84 坐标系下的经纬度，精度取决于输入完整度 | 不提供 GCJ-02 或 BD-09 坐标转换 |
| 批量处理 | 单次调用处理一条地址；支持循环调用 | 不支持流式批量接口 |
| 离线能力 | 纯规则解析部分可离线运行 | 坐标匹配依赖在线地理编码服务 |

**适用对象**：需要将用户输入的地址转换为坐标的开发者、需要清洗地址数据的分析师、需要标准化地址格式的业务系统。

**边界值说明**：
- 地址长度超过 200 字符时，超出部分将被截断并标记 `[需核实:截断]`
- 置信度低于 0.4 时，坐标字段返回空值，仅返回结构化组件
- 输入为空字符串或纯空白时，返回错误码 `E1001`

## 三、标准处理流程

### 前置条件

1. 输入必须为字符串类型，编码为 UTF-8
2. 地址中不得包含 HTML 标签或 URL
3. 若需坐标匹配，确保网络可访问地理编码服务

### 执行步骤

**步骤 1：输入接收与预处理**

- 去除首尾空白字符
- 统一全角/半角符号（逗号、句号、括号）
- 检测并移除多余空格（保留"XX 路 XX 号"中的必要空格）

**步骤 2：地址结构解析**

按以下优先级顺序拆分地址组件：

```
省级 → 市级 → 区/县级 → 街道/乡镇 → 路/巷 → 门牌号 → 楼栋/单元/房间
```

解析规则示例：

| 输入片段 | 识别规则 | 输出组件 |
|---------|---------|---------|
| "北京市" | 以"省/市/自治区"结尾 | province: "北京市" |
| "海淀区" | 以"区/县/市"结尾 | district: "海淀区" |
| "中关村大街 27 号" | 包含"路/街/大道/巷" + 数字 | street: "中关村大街", number: "27号" |
| "A 座 1203 室" | 包含"座/栋/幢/号楼" + "室/房" | building: "A座", room: "1203室" |

**步骤 3：坐标匹配与置信度计算**

- 将完整地址文本发送至地理编码服务
- 同时将"省+市+区"三级组合作为降级查询条件
- 置信度计算规则：

| 匹配情况 | 置信度 |
|---------|--------|
| 完整地址精确匹配 | 0.9 - 1.0 |
| 省市区匹配 + 街道模糊匹配 | 0.7 - 0.89 |
| 仅省市区匹配 | 0.5 - 0.69 |
| 仅省市匹配 | 0.3 - 0.49 |
| 无法匹配 | < 0.3（坐标返回空） |

**步骤 4：输出规范化**

按以下 JSON 结构输出：

```json
{
  "status": "success",
  "input": "原始地址字符串",
  "parsed": {
    "province": "省/直辖市",
    "city": "市",
    "district": "区/县",
    "street": "街道/路名",
    "number": "门牌号",
    "building": "楼栋信息",
    "room": "房间号"
  },
  "coordinates": {
    "lat": 39.9042,
    "lng": 116.4074
  },
  "confidence": 0.95,
  "match_level": "full_address"
}
```

**输出规范**：
- 所有字段均返回字符串类型（坐标除外）
- 无法解析的组件返回空字符串 `""`
- 坐标保留 6 位小数
- 置信度保留 2 位小数

## 四、置信度门控机制

当信息不足或存在歧义时，本技能遵循**不编造原则**：

| 场景 | 处理方式 | 输出示例 |
|------|---------|---------|
| 缺少门牌号 | 坐标返回，置信度降至 0.7 以下 | `"number": "", "confidence": 0.65` |
| 区级信息缺失 | 尝试用市级匹配，置信度 ≤ 0.5 | `"district": "", "confidence": 0.45` |
| 地址过于模糊（仅城市名） | 坐标返回空，标记需核实 | `"coordinates": {}, "confidence": 0.3` |
| 存在多个同名地点 | 返回第一个匹配，并标注 | `"note": "[需核实:存在多个同名地点]"` |
| 地址中包含无法识别的符号 | 保留原样，标记该字段 | `"street": "[需核实:无法解析的符号]中关村大街"` |

**强制规则**：任何情况下，不得虚构坐标或置信度。若无法匹配，坐标字段返回空对象 `{}`，并在 `note` 字段中说明原因。

## 六、FAQ 与反模式对照

### 常见坑 1：忽略行政区划层级

**错误做法**：直接输入"中关村大街 27 号"期望得到精确坐标。

**正确做法**：补充省市信息，如"北京市海淀区中关村大街 27 号"。

**反模式**：`"北京市中关村大街"` → 缺少区级信息，置信度仅 0.5。

### 常见坑 2：混淆坐标体系

**错误做法**：将输出的 WGS-84 坐标直接用于高德地图（需 GCJ-02）。

**正确做法**：确认使用场景，必要时进行坐标转换。

**反模式**：`"lat": 39.9042` 直接标注为"百度坐标"。

### 常见坑 3：地址中包含多余信息

**错误做法**：输入"北京市海淀区中关村大街 27 号（靠近地铁 4 号线）"。

**正确做法**：去除括号内的辅助说明，仅保留地址主体。

**反模式**：括号内容被解析为街道名称的一部分。

### 常见坑 4：期望处理非地址文本

**错误做法**：输入"张三的收货地址是北京市朝阳区"。

**正确做法**：仅输入地址部分"北京市朝阳区"。

**反模式**：人名被解析为街道名称。

### 常见坑 5：忽略置信度直接使用坐标

**错误做法**：置信度 0.45 的坐标直接用于精确导航。

**正确做法**：置信度低于 0.7 时，应提示用户确认或补充信息。

**反模式**：`"confidence": 0.45` 仍被当作精确坐标使用。
