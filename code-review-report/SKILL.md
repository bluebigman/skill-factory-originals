# 代码审查报告 Skill（code-review-report）

## 一、能力边界：一页纸速查卡

本 Skill 专注于**代码变更（diff）**的结构化审查，不处理完整代码库的全局评估。

| 维度 | 能做 ✅ | 不能做 ❌ |
|------|--------|----------|
| **输入** | 接受统一 diff 格式文本、Git 输出、文件路径列表 | 不直接连接 Git 仓库拉取代码（需用户提供差异内容） |
| **分析范围** | 变更行及其直接影响区域（函数体、调用链） | 不做全量代码库的架构评估或跨模块深层依赖分析 |
| **问题识别** | 逻辑缺陷、安全漏洞、性能隐患、规范偏差 | 不提供自动化修复补丁，只输出建议方向 |
| **输出** | 分级问题清单（严重/警告/提示）、置信度标注 | 不生成代码质量评分或通过/失败的硬性结论 |
| **扩展** | 支持批量多文件 diff 审查、自定义输出格式 | 无法识别图片、二进制文件或非文本格式的变更 |

**适用对象**：进行 MR/PR 评审的开发者、技术负责人、DevOps 流程中的质量检查环节。

## 三、标准流程：从输入到报告

### 前置条件
- 输入内容必须是**纯文本 diff**（统一 diff 格式）或**可访问的文件路径**
- 若提供文件路径，需确保文件存在且为文本类源码文件
- 建议附带审查重点（如"重点看登录模块"），否则将全面扫描

### 执行步骤（分步编号）

**Step 1：输入解析与确认**
- 识别输入类型：`diff文本` 或 `文件路径`
- 若为路径，读取文件并生成内部 diff 对比（需用户提供基线版本）
- 检查格式：缺少 `---`/`+++` 头信息时，标记为 `[需核实:diff格式]`

**Step 2：变更区域定位**
- 提取变更的文件名、函数名、行号范围
- 忽略纯空白/缩进改动（除非与规范相关）
- 构建变更上下文：前后各保留 3-5 行作为分析背景

**Step 3：四维问题扫描**
按以下优先级逐项检查（每项含具体参数）：

| 检查维度 | 关键扫描点 | 示例参数/边界 |
|---------|-----------|--------------|
| **逻辑缺陷** | 空指针、边界条件、状态未更新、错误处理遗漏 | 数组越界（index >= length）、循环条件不变量破坏 |
| **安全漏洞** | 注入（SQL/XSS/命令）、敏感信息硬编码、权限缺失 | 拼接字符串进 SQL、密码/密钥出现在 diff 中、未校验用户角色 |
| **性能问题** | 循环内 I/O、N+1 查询、内存泄漏风险、死循环 | 循环内调用外部 API、递归无终止条件、大对象未释放 |
| **规范偏差** | 命名风格、缩进、注释缺失、魔法数字、TODO 遗留 | 项目约定 camelCase 但使用 snake_case、硬编码 86400 秒 |

**Step 4：置信度标注**
- 每条问题附 `[高置信]` / `[中置信]` / `[需核实:字段名]`
- 规则：
  - 确定性问题（如语法错误）→ 高置信
  - 推断性问题（如潜在 N+1）→ 中置信
  - 信息不足（如缺少调用方代码）→ `[需核实:调用方逻辑]`

**Step 5：输出规范与自查**
- 按 Markdown 表格输出（见下方模板）
- 自查清单：字段完整性、格式正确性、置信度标注是否齐全
- 若输入无法解析，返回错误提示（见第五节）

### 输出模板

```markdown

| 🟡 提示 | config.py | 15 | 规范 | 魔法数字 86400 | 提取为常量 | 高置信 |
```

## 四、置信度门控：不编造原则

当信息不足以做出判断时，**必须**使用 `[需核实:具体字段]` 占位，并明确说明缺失的信息。

| 场景 | 处理方式 | 示例输出 |
|------|----------|----------|
| diff 缺少上下文 | 标记无法判断逻辑完整性 | `[需核实:函数完整实现]` |
| 依赖外部接口未提供 | 标注外部依赖假设 | `[需核实:第三方API返回结构]` |
| 配置项取值未知 | 不做默认假设 | `[需核实:生产环境配置值]` |

**禁止行为**：
- 猜测缺失信息并当作事实输出
- 使用"可能"、"大概"等模糊词替代结构化置信度标注
- 对不确定项给出"修复建议"
