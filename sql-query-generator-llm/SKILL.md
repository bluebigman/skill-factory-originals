## 三、标准处理流程

### 前置条件

在发起请求前，请确认以下信息是否齐备：

| 信息类型 | 是否必需 | 示例 |
|----------|----------|------|
| 表名 | ✅ 必需 | `users`、`orders` |
| 字段名 | ✅ 必需 | `id`、`name`、`created_at` |
| 查询意图 | ✅ 必需 | 筛选、排序、聚合、关联 |
| 数据库类型 | ⚠️ 建议提供 | MySQL / PostgreSQL / SQLite（默认 ANSI SQL） |
| 过滤条件值 | ⚠️ 视情况 | 具体数值、字符串、日期范围 |

### 执行步骤

**步骤 1：解析输入内容**

- 提取表名、字段名、操作类型（增删改查）
- 识别条件表达式、排序字段、聚合函数
- 标记缺失的关键信息

**步骤 2：确定 SQL 语句类型**

| 用户意图 | 生成的语句类型 |
|----------|----------------|
| 查询/筛选/统计 | SELECT |
| 添加/插入 | INSERT |
| 更新/修改 | UPDATE |
| 删除/移除 | DELETE |
| 创建表/结构 | CREATE TABLE |

**步骤 3：组装 SQL 语句**

- 按标准语法结构拼接各子句
- 根据数据库方言调整引号、分页语法等细节
- 对字符串值添加单引号，数值不加引号

**步骤 4：输出与标注**

- 每条生成的 SQL 前标注序号
- 对不确定的字段值使用 `[需核实:字段名]` 占位符
- 在语句末尾附注生成依据和假设条件

## 六、FAQ 与反模式对照

### 常见坑 1：字段名猜测

- **错误做法**：用户说"查一下用户信息"，直接生成 `SELECT * FROM users`
- **正确做法**：询问需要哪些具体字段，或使用 `SELECT *` 并标注"已使用通配符，建议明确字段列表"

### 常见坑 2：忽略数据库方言

- **错误做法**：默认使用 MySQL 语法，但用户实际使用 SQLite
- **正确做法**：主动询问数据库类型，或生成 ANSI 标准 SQL 并注明兼容性

### 常见坑 3：字符串值不加引号

- **错误做法**：`WHERE name = 张三`（未加引号）
- **正确做法**：`WHERE name = '张三'`，并说明字符串值必须加单引号

### 常见坑 4：多表关联条件缺失

- **错误做法**：直接生成 `FROM users, orders` 笛卡尔积
- **正确做法**：要求提供关联字段，生成 `JOIN ... ON users.id = orders.user_id`

### 常见坑 5：输入信息过载

- **错误做法**：一次性输入 10 条查询需求，期望一次全部生成
- **正确做法**：建议分批处理，每次 3-5 条，便于逐条校验

### 示例 1：基础查询

**用户输入**：从 employees 表中查询工资大于 5000 的员工姓名和工资

**生成结果**：

```sql

FROM employees
WHERE salary > 5000;
```

### 示例 2：多表关联

**用户输入**：查询每个客户的订单数量，客户表 customers，订单表 orders

**生成结果**：

```sql
SELECT c.customer_name, COUNT(o.order_id) AS order_count
FROM customers c
LEFT JOIN orders o ON c.customer_id = o.customer_id
GROUP BY c.customer_name;
```
