## 三、标准流程

### 3.1 前置条件

| 条件 | 要求 | 缺失时的处理 |
|------|------|--------------|
| 目标 URL | 必须是可公开访问的 HTTP/HTTPS 地址 | 提示用户提供完整 URL |
| 页面结构 | 目标页面需为静态 HTML 或可预渲染 | 提示用户先完成预渲染 |
| 字段定义 | 至少指定 1 个待提取字段 | 提示用户描述需要哪些数据 |
| 输出格式 | 默认为 JSON，可选 CSV | 无需额外配置 |

### 3.2 执行步骤

**Step 1 — 需求解析**

将用户描述转换为结构化采集意图：

```
输入示例：
“打开 https://example.com/products，提取每个商品的名称、价格、评价数，
翻页 3 次，下一页按钮是 .pagination .next，输出 JSON。”

解析结果：
{
  "entry_url": "https://example.com/products",
  "fields": ["name", "price", "review_count"],
  "pagination": {"type": "css_click", "selector": ".pagination .next", "max_pages": 3},
  "output_format": "json"
}
```

**Step 2 — 流程生成**

根据解析结果生成采集流程定义（伪代码）：

```
flow = [
  {action: "open", url: "https://example.com/products"},
  {action: "extract", fields: ["name", "price", "review_count"]},
  {action: "paginate", selector: ".pagination .next", max_pages: 3},
  {action: "export", format: "json"}
]
```

**Step 3 — 单样本试运行**

- 仅对第 1 条记录执行提取
- 展示提取结果，标注每个字段的提取状态（成功/为空/超时）
- 若字段为空，提示用户检查选择器

**Step 4 — 字段校验**

| 校验项 | 通过标准 | 失败处理 |
|--------|----------|----------|
| 字段非空率 | ≥ 90% | 提示用户调整选择器或清洗规则 |
| 字段格式 | 符合预期类型（数字/字符串/日期） | 提示用户添加清洗规则 |
| 去重率 | 重复记录 ≤ 5% | 提示用户检查翻页逻辑 |

**Step 5 — 批量执行**

- 按流程定义循环执行，每页间隔 1-2 秒
- 实时输出进度：`已采集 45/150 条`
- 异常时自动重试 2 次，仍失败则跳过并记录

**Step 6 — 结果抽查**

- 按 5% 比例随机抽样（最少 10 条）
- 输出抽查报告：每条记录的字段完整度、格式正确性
- 标注异常记录，供用户人工复核

### 3.3 输出规范

## 六、FAQ 反模式

### 6.1 常见坑与反模式对照

| 常见坑 | 反模式（错误做法） | 正确做法 |
|--------|-------------------|----------|
| 选择器失效 | 直接批量执行，不先试运行 | 先跑单样本，确认字段非空再批量 |
| 翻页死循环 | 不设最大翻页次数 | 始终设置 `max_pages`，默认 10 页上限 |
| 数据重复 | 翻页后不清除已提取数据 | 每次翻页前重置当前页数据容器 |
| 字段错位 | 依赖固定索引取值 | 使用语义化选择器（类名、ID、属性） |
| 请求过快 | 不设请求间隔 | 每页间隔 1-2 秒，避免触发反爬 |

### 6.2 反模式示例

**反模式 1：跳过试运行**

```
用户：直接抓吧，不用试。
错误：立即执行批量采集 → 发现选择器错误 → 全部数据无效
正确：先跑 1 条 → 确认字段正确 → 再批量执行
```

**反模式 2：无限翻页**

```
用户：把所有页都抓完。
错误：不设 max_pages → 遇到“下一页”按钮永远存在 → 死循环
正确：设置 max_pages=20 → 达到上限自动停止 → 检查是否抓完
```

**反模式 3：忽略异常记录**

```
用户：抓完就行，不用管报错的。
错误：跳过所有失败记录 → 数据不完整 → 分析结果偏差
正确：记录失败原因 → 输出部分失败报告 → 人工补采
```
