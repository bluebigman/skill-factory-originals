## 三、标准流程

### 3.1 前置条件

输入数据必须包含以下字段（JSON 数组格式）：

| 字段名 | 类型 | 必填 | 说明 |
|--------|------|------|------|
| `name` | string | 是 | 任务名称，唯一标识 |
| `duration` | number | 是 | 工期（天），必须为正整数 |
| `dependencies` | array | 否 | 依赖的任务名称列表，默认为空 |
| `resource` | string | 否 | 资源名称（人/设备），默认为空 |
| `deadline` | string | 否 | 截止日期，格式 `YYYY-MM-DD` |

**示例输入：**

```json
[
  {"name": "需求分析", "duration": 3, "resource": "张三"},
  {"name": "原型设计", "duration": 5, "dependencies": ["需求分析"], "resource": "李四"},
  {"name": "UI设计", "duration": 4, "dependencies": ["原型设计"], "resource": "李四"},
  {"name": "开发", "duration": 10, "dependencies": ["原型设计"], "resource": "王五"},
  {"name": "测试", "duration": 4, "dependencies": ["开发"], "deadline": "2025-06-30"}
]
```

### 3.2 执行步骤

1. **解析输入**：将输入内容解析为任务数组，校验字段完整性。
2. **构建依赖图**：根据 `dependencies` 字段建立任务间的有向无环图（DAG）。
3. **拓扑排序**：对任务进行拓扑排序，确定执行顺序；若检测到环，返回错误码 `E1002`。
4. **正向推算**：从无依赖任务开始，计算每个任务的最早开始时间（ES）与最早结束时间（EF）。
5. **反向推算**：从末端任务开始，计算每个任务的最晚开始时间（LS）与最晚结束时间（LF）。
6. **计算浮动时间**：`浮动时间 = LS - ES`（或 `LF - EF`）。
7. **识别关键路径**：标记所有浮动时间为零的任务，按依赖顺序串联为关键路径。
8. **检测资源冲突**：遍历所有任务对，检查是否存在相同资源且时间段重叠。
9. **生成延期预警**：对设置了 `deadline` 的任务，比较 EF 与 deadline，若 EF > deadline 则预警。
10. **渲染输出**：按 3.3 节规范输出甘特图、关键路径、冲突列表与预警列表。

### 3.3 输出规范

输出包含以下四个部分，顺序固定：

#### 第一部分：排期总览表

| 任务名称 | 开始日期 | 结束日期 | 工期(天) | 浮动时间(天) | 是否关键 |
|----------|----------|----------|----------|--------------|----------|
| 需求分析 | 2025-06-01 | 2025-06-03 | 3 | 0 | 是 |
| 原型设计 | 2025-06-04 | 2025-06-08 | 5 | 0 | 是 |
| ... | ... | ... | ... | ... | ... |

#### 第二部分：文本甘特图

```
任务名称        | 6/01  6/05  6/10  6/15  6/20  6/25  6/30
----------------|------------------------------------------
需求分析        | ███
原型设计        |       █████
UI设计          |             ████
开发            |       ██████████
测试            |                         ████
```

> 注：`█` 表示任务执行区间，` ` 表示空闲。刻度按天自动缩放。

#### 第三部分：关键路径

```
关键路径（总工期：26天）：
需求分析 → 原型设计 → 开发 → 测试
```

#### 第四部分：冲突与预警

```

- 李四：UI设计(6/09-6/12) 与 开发(6/09-6/18) 冲突，重叠 4 天
```

## 六、FAQ 与反模式

### 6.1 常见坑

| 坑 | 反模式（错误做法） | 正模式（正确做法） |
|----|-------------------|-------------------|
| 依赖关系遗漏 | 任务 B 实际依赖 A，但未声明，导致排期提前 | 显式声明 `"dependencies": ["A"]` |
| 资源命名不一致 | 同一人有时写"张三"，有时写"张 三" | 统一资源名称，避免空格或别名 |
| 工期单位混淆 | 将"人天"误写为"天" | 明确工期单位，本 Skill 默认按自然日计算 |
| 忽略浮动时间 | 认为所有任务都必须尽快开始 | 非关键任务可适当延迟，不影响总工期 |
| 截止日期设置过紧 | 所有任务都设 deadline，导致预警过多 | 仅对里程碑或交付节点设置 deadline |

### 6.2 反模式对照

| 反模式 | 后果 | 替代方案 |
|--------|------|----------|
| 输入 100+ 个任务一次性计算 | 输出冗长，难以阅读 | 拆分为多个子项目分别计算 |
| 依赖关系超过 3 层嵌套 | 排期表复杂，可读性差 | 合并中间任务或使用里程碑 |
| 资源冲突不处理直接交付 | 实际执行时资源超载 | 先解决冲突再输出最终排期 |
| 不设置任何 deadline | 无法触发延期预警 | 至少为关键任务设置 deadline |
