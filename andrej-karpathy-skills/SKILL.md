## 三、标准执行流程

### 3.1 前置条件

| 条件 | 要求 | 不满足时的处理 |
|------|------|---------------|
| 项目目录可访问 | 有读取权限 | 报错 E-101，提示检查权限 |
| 代码文件存在 | 至少 1 个源码文件 | 报错 E-102，提示空项目 |
| 依赖清单可识别 | 能识别常见格式 | 报错 E-103，提示手动指定 |
| 磁盘空间充足 | ≥ 50MB 可用 | 报错 E-104，提示清理空间 |

### 3.2 执行步骤（分步编号）

**步骤 1：环境感知（约 5 秒）**

1. 扫描项目根目录，生成文件树
2. 排除以下目录：`node_modules`、`.git`、`venv`、`__pycache__`、`dist`、`build`、`.next`、`.cache`
3. 识别依赖清单文件：
   - `package.json`（Node.js）
   - `requirements.txt` / `pyproject.toml`（Python）
   - `go.mod`（Go）
   - `pom.xml` / `build.gradle`（Java）
   - `Cargo.toml`（Rust）
4. 若存在 `.git` 目录，读取最近 10 条提交记录（`git log --oneline -10`）

**步骤 2：规范基准加载（约 2 秒）**

1. 检查项目根目录是否存在 `.coding-standards.md`
2. 若存在：
   - 解析 YAML frontmatter（如 `strictness: high`）
   - 提取正文章节中的规范条目
   - 合并到检查流程作为补充判定依据
3. 若不存在：使用内置默认规范（宽松模式）
4. 若格式错误：报错 E-106，回退到内置默认规范

**步骤 3：任务拆解评估（约 3 秒）**

对当前工作区中的改动进行评估：

| 评估维度 | 判定标准 | 标记 |
|---------|---------|------|
| 任务过大 | 单次改动超过 200 行代码 | ⚠️ 过大 |
| 任务碎片化 | 单次改动少于 5 行但涉及 10 个以上文件 | ⚠️ 碎片化 |
| 合理粒度 | 单次改动 20-200 行，涉及 1-5 个文件 | ✅ 合理 |

**步骤 4：验证反馈闭环检测（约 3 秒）**

1. 检查最近 3 次修改记录
2. 确认每次修改后是否执行了测试命令
3. 测试命令识别模式：
   - `npm test` / `yarn test` / `pnpm test`
   - `pytest` / `python -m pytest`
   - `go test`
   - `mvn test` / `gradle test`
   - `cargo test`
4. 若最近 3 次修改均无测试记录 → 标记为"闭环断裂"

**步骤 5：缺陷模式扫描（约 10 秒）**

对项目源码执行 7 类缺陷模式扫描：

| 编号 | 缺陷类型 | 典型特征 |
|------|---------|---------|
| D-01 | 幻觉 API 调用 | 调用了不存在的库函数或方法 |
| D-02 | 上下文丢失 | 修改 A 处导致 B 处逻辑不一致 |
| D-03 | 过度工程化 | 为简单需求引入了复杂抽象 |
| D-04 | 复制粘贴残留 | 未修改的注释、变量名、硬编码值 |
| D-05 | 错误处理缺失 | 未捕获可能的异常或边界条件 |
| D-06 | 性能盲区 | 在循环中执行高开销操作 |
| D-07 | 安全疏忽 | 硬编码密钥、SQL 注入、XSS 风险 |

**步骤 6：报告生成（约 5 秒）**

按 3.3 节输出规范生成完整报告。

### 3.3 输出规范

报告必须包含以下 5 个部分：

**第一部分：摘要**

- 检查范围（扫描的文件数、代码行数）
- 发现的问题总数
- 严重程度分布（高/中/低）

**第二部分：缺陷明细**

每条缺陷包含：

| 字段 | 说明 |
|------|------|
| 编号 | 如 D-01-001 |
| 位置 | 文件路径 + 行号 |
| 描述 | 缺陷具体表现 |
| 证据 | 代码片段或日志 |
| 修复建议 | 具体操作步骤 |

**第三部分：上下文评估**

- 上下文使用率（当前 token 使用 / 最大可用）
- 约束保留情况（规范基准中哪些条目被遵守/违反）
- 任务拆解评分（1-10 分）

**第四部分：行动清单**

按优先级排列：

| 优先级 | 行动项 | 预期效果 |
|--------|--------|---------|
| P0 | 立即修复高危缺陷 | 消除阻断性问题 |
| P1 | 补充缺失的测试 | 恢复验证闭环 |
| P2 | 调整任务拆解策略 | 提升协作效率 |
| P3 | 更新规范基准 | 预防同类问题 |

**第五部分：置信度标注**

- 每条结论标注置信度（高/中/低）
- 低置信度结论使用 `[需核实:字段]` 占位
- 示例：`[需核实:该函数在 v2.3.0 版本中的行为]`

## 四、置信度门控机制

### 4.1 置信度分级标准

| 级别 | 判定标准 | 输出格式 |
|------|---------|---------|
| 高 | 有直接代码证据 + 可复现 | 直接给出结论 |
| 中 | 有间接证据或推断 | 标注"可能" |
| 低 | 信息不足或推测 | 使用 `[需核实:...]` 占位 |

### 4.2 信息不足时的处理

当遇到以下情况时，必须使用占位符而非编造：

1. 无法确定某个 API 的确切行为 → `[需核实:该 API 在目标环境中的实际行为]`
2. 不确定某处修改是否影响其他模块 → `[需核实:修改对模块 X 的潜在影响]`
3. 无法确认测试覆盖率 → `[需核实:当前测试覆盖率数据]`
4. 依赖版本不明确 → `[需核实:依赖包 X 的实际版本]`

### 4.3 占位符使用规则

- 每个报告最多允许 5 个占位符
- 占位符必须包含具体字段名
- 占位符不得用于替代核心结论
- 用户提供补充信息后，占位符可升级为正式结论

## 五、错误码体系

### 5.1 错误码总表

| 错误码 | 错误描述 | 提示话术 | 修正步骤 |
|--------|---------|---------|---------|
| E-101 | 目录权限不足 | "无法读取项目目录，请检查权限设置" | 1. 检查目录权限 2. 使用 `chmod` 调整 3. 重新运行 |
| E-102 | 空项目 | "未检测到任何源码文件" | 1. 确认项目路径正确 2. 检查是否为空目录 3. 添加源码后重试 |
| E-103 | 依赖清单无法识别 | "无法识别依赖清单格式" | 1. 确认依赖文件存在 2. 检查文件格式 3. 手动指定依赖文件路径 |
| E-104 | 磁盘空间不足 | "可用磁盘空间不足 50MB" | 1. 清理临时文件 2. 释放磁盘空间 3. 重新运行 |
| E-105 | Git 仓库损坏 | "无法读取 Git 提交记录" | 1. 检查 `.git` 目录完整性 2. 运行 `git fsck` 修复 3. 跳过 Git 分析继续 |
| E-106 | 规范文件格式错误 | "`.coding-standards.md` 格式错误，已回退到默认规范" | 1. 检查 YAML frontmatter 格式 2. 修正后重新运行 3. 或删除该文件使用默认规范 |
| E-107 | 扫描超时 | "扫描超过 60 秒，已中断" | 1. 减少扫描范围 2. 排除大文件目录 3. 分批扫描 |
| E-108 | 输出目录不可写 | "无法写入报告文件" | 1. 检查输出目录权限 2. 更换输出路径 3. 重试 |

### 5.2 错误处理流程

```
遇到错误
  ↓
记录错误码和上下文
  ↓
输出提示话术
  ↓
给出修正步骤
  ↓
等待用户操作
  ↓
重新执行或跳过
```

## 六、FAQ 反模式对照

### 6.1 常见坑与反模式

| 坑编号 | 常见错误做法 | 反模式特征 | 正确做法 |
|--------|-------------|-----------|---------|
| F-01 | 忽略上下文直接改代码 | 不看项目结构、不读依赖清单就动手 | 先执行环境感知，再开始修改 |
| F-02 | 一次改太多文件 | 单次提交涉及 20+ 文件 | 拆分为多个逻辑独立的提交 |
| F-03 | 改完不跑测试 | 修改后直接提交，无验证步骤 | 每次修改后至少运行一次相关测试 |
| F-04 | 复制代码不检查 | 从其他项目粘贴代码未适配 | 检查复制代码的依赖和上下文 |
| F-05 | 忽略规范文件 | 项目有 `.coding-standards.md` 但不读 | 每次开始前加载规范基准 |
| F-06 | 编造不确定信息 | 对不确定的 API 行为直接下结论 | 使用 `[需核实:...]` 占位符 |
| F-07 | 过度设计 | 为简单需求引入微服务架构 | 遵循 YAGNI 原则，保持简单 |

### 6.2 反模式自查清单

每次 AI 协作编码后，对照以下清单自查：

- [ ] 是否理解了项目整体结构？
- [ ] 是否检查了依赖清单？
- [ ] 是否阅读了 `.coding-standards.md`？
- [ ] 改动是否在合理粒度范围内（20-200 行）？
- [ ] 是否执行了测试验证？
- [ ] 是否有不确定的信息被编造？
- [ ] 是否有复制粘贴的代码未适配？

## 八、内置默认规范（无 `.coding-standards.md` 时使用）

### 8.1 代码风格

- 缩进：2 空格（JS/TS），4 空格（Python/Java）
- 命名：camelCase（JS/TS），snake_case（Python）
- 行宽：不超过 100 字符
- 引号：单引号（JS/TS），双引号（Python）

### 8.2 提交规范

- 提交信息格式：`type(scope): description`
- type 可选值：`feat` / `fix` / `docs` / `style` / `refactor` / `test` / `chore`
- 每次提交只包含一个逻辑变更

### 8.3 测试要求

- 新增功能必须有对应测试
- 修改代码必须运行相关测试
- 测试覆盖率不低于 70%
