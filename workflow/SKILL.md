## 三、标准执行流程

### 3.1 前置条件

| 条件 | 要求 | 检查方式 |
|------|------|----------|
| 文件位置 | 所有待处理文件必须位于同一目录 | 执行 `ls` 确认 |
| 命名规范 | 文件名前缀一致（如 `input_*.csv`） | 执行 `ls | grep 前缀` |
| 格式声明 | 明确告知输入格式与目标格式 | 用户需在请求中说明 |
| 备份空间 | 目录至少有 2 倍源文件大小的可用空间 | 执行 `df -h` 确认 |

### 3.2 执行步骤

**步骤 1：输入清点**

1. 列出目录内所有文件，记录文件名、大小、修改时间。
2. 与用户确认处理范围（全部文件或指定子集）。
3. 生成文件清单表：

   ```
   | 文件名 | 大小(KB) | 行数 | 格式 |
   |--------|----------|------|------|
   | a.csv  | 12       | 340  | CSV  |
   | b.json | 8        | 120  | JSON |
   ```

**步骤 2：模板定义**

1. 根据用户目标格式，定义输出字段模板。
2. 模板示例（以 JSON 输出为例）：

   ```json
   {
     "record_id": "string",
     "timestamp": "YYYY-MM-DD HH:mm:ss",
     "source_file": "string",
     "content": "object"
   }
   ```

3. 与用户确认模板字段是否完整。

**步骤 3：试运行**

1. 取第一条记录执行转换。
2. 输出试运行结果，并附字段映射对照表：

   | 源字段 | 目标字段 | 转换规则 | 状态 |
   |--------|----------|----------|------|
   | name   | record_id | 前缀加 `ID_` | ✅ |
   | date   | timestamp | 格式化为标准时间 | ✅ |

3. 用户确认无误后进入下一步。

**步骤 4：批量执行**

1. 对全量数据执行转换。
2. 转换前自动复制源文件至 `./backup_YYYYMMDD/` 目录。
3. 输出结果写入 `./output/` 目录，文件名规则：`converted_<原文件名>`。

**步骤 5：结果校验**

1. 随机抽取 5% 或至少 3 条记录（取较大值）。
2. 比对源数据与输出数据，核对关键字段。
3. 生成校验报告：

   ```
   校验时间：2025-01-15 14:30
   抽样数量：5
   通过数量：4
   差异数量：1
   差异详情：
     - 记录 ID_0032：timestamp 字段源为 "2024/12/31"，输出为 "2024-12-31 00:00:00"，格式已统一，内容一致。
   ```

### 3.3 输出规范

| 输出项 | 格式 | 说明 |
|--------|------|------|
| 转换结果 | JSON / CSV / Markdown | 与用户约定的目标格式 |
| 校验报告 | Markdown 表格 | 含抽样数量、通过率、差异明细 |
| 备份目录 | 文件夹 | 路径为 `./backup_YYYYMMDD/` |
| 执行日志 | 文本文件 | 记录每步操作时间与结果 |

## 四、置信度门控

### 4.1 占位符规则

当源数据缺失或无法确认时，**禁止编造内容**。使用以下占位符标记：

| 场景 | 占位符 | 示例 |
|------|--------|------|
| 字段缺失 | `[需核实:字段名]` | `"phone": "[需核实:phone]"` |
| 格式不确定 | `[需核实:格式]` | `"date": "[需核实:格式]"` |
| 内容无法解析 | `[需核实:内容]` | `"address": "[需核实:内容]"` |

### 4.2 门控触发条件

- 源数据中某字段为空且无默认值约定 → 使用占位符
- 源数据格式与模板不匹配且无法推断 → 使用占位符
- 链接内容抓取失败（404、超时）→ 在结果中标注 `[需核实:链接不可达]`

### 4.3 占位符处理流程

1. 转换时发现缺失 → 立即填入占位符
2. 校验阶段列出所有占位符位置
3. 输出最终结果时，附「待核实清单」：

   ```
   待核实清单：
   1. 记录 ID_0007 的 phone 字段缺失
   2. 记录 ID_0012 的 date 格式无法识别
   ```

## 六、FAQ 与反模式对照

### 6.1 常见坑

| 坑 | 反模式（错误做法） | 正确做法 |
|----|-------------------|----------|
| 直接全量执行 | 跳过试运行，直接处理全部文件 | 必须先用单条样本验证，确认后再批量 |
| 覆盖原始文件 | 转换后直接覆盖源文件 | 始终保留备份目录，源文件只读 |
| 忽略字段缺失 | 缺失字段自动填 `null` 或空字符串 | 使用 `[需核实:字段]` 占位符，并在报告中列出 |
| 格式猜测 | 根据文件内容猜测格式，不询问用户 | 执行前明确确认输入/输出格式 |
| 无校验直接交付 | 转换完直接输出，不做抽查 | 至少抽样 5% 或 3 条记录进行比对 |

### 6.2 反模式对照表

| 反模式 | 问题 | 替代方案 |
|--------|------|----------|
| "我猜这个字段应该是日期" | 猜测可能导致数据错误 | 使用占位符并询问用户 |
| "全部处理完再说" | 错误会放大到全量数据 | 先试运行，确认后再批量 |
| "直接覆盖吧，省事" | 数据丢失无法恢复 | 强制备份机制 |
| "这个字段不重要，删掉" | 用户可能后续需要该字段 | 保留字段并标记 `[需核实:保留]` |
| "格式差不多就行" | 格式不一致导致下游解析失败 | 严格按模板输出，格式不符即报错 |
