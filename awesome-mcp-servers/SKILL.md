# awesome-mcp-servers 技能文档

## 一、能力边界：一页纸速查卡

本技能用于**整理、筛选和呈现 MCP（Model Context Protocol）服务器资源信息**。它不直接连接或调用任何 MCP 服务器，而是作为一份智能化的资源索引与能力速查手册。

| 维度 | 说明 |
|------|------|
| **核心用途** | 将用户提供的 MCP 服务器列表、仓库链接或描述文本，转化为结构化的能力速查表 |
| **输入来源** | 用户粘贴的文本、上传的 Markdown/JSON 文件、公开的 GitHub 仓库 URL |
| **输出产物** | 按分类组织的 MCP 服务器清单，含能力标签、接入难度、适用场景 |
| **处理深度** | 识别服务器名称、核心功能、依赖要求、适用平台等关键字段 |
| **批量能力** | 支持一次处理 10-50 条服务器记录，自动去重与归类 |

### 能做（5 项核心能力）

1. **结构化提取**：从非结构化文本中识别 MCP 服务器名称、用途描述、协议版本、传输方式（stdio/SSE/Streamable HTTP）。
2. **能力标签化**：为每个服务器生成 3-5 个能力标签（如 `文件访问`、`数据库`、`搜索`、`代码执行`）。
3. **分类归组**：按功能领域（开发工具、数据存储、通信协作、AI 增强等）自动分组。
4. **接入参数解析**：提取环境变量要求、启动命令、依赖项等接入关键信息。
5. **对比速查输出**：生成 Markdown 或 JSON 结构，便于快速浏览与决策。

### 不能做（明确边界）

| 限制项 | 说明 |
|--------|------|
| 不执行代码 | 不会实际启动或测试任何 MCP 服务器 |
| 不验证可用性 | 不保证列出的服务器当前在线或维护状态 |
| 不提供安全审计 | 不审查服务器代码安全性，仅做信息整理 |
| 不保证完整性 | 仅处理用户提供的信息，不主动爬取全网资源 |
| 不替代官方文档 | 详细配置请以各服务器官方 README 为准 |

### 适用对象

- 正在选型 MCP 服务器的开发者
- 需要快速了解团队已有 MCP 资产的技术负责人
- 撰写 MCP 相关技术文档或教程的内容创作者

## 三、标准流程：从输入到输出

### 前置条件

- 用户提供了至少 1 条 MCP 服务器相关信息（名称、URL、描述任一即可）
- 输入内容可被文本解析（纯文本、Markdown、JSON 均可）
- 若提供 URL，需确保可公开访问

### 执行步骤

**步骤 1：收集与确认输入**

接收用户输入，确认以下信息：

| 参数 | 必填 | 默认值 | 说明 |

| `output_format` | 否 | `markdown` | 可选 `markdown` / `json` |

| `detail_level` | 否 | `standard` | 可选 `brief` / `standard` / `full` |

**步骤 2：解析与识别**

- 提取服务器名称（通常为仓库名或包名）
- 识别描述文本中的功能关键词
- 检测协议类型（`stdio`、`SSE`、`HTTP`）
- 标记依赖要求（如 `Python 3.9+`、`Node.js 18+`）

**步骤 3：结构化处理**

按以下规则处理：

1. 去重：相同名称或相同仓库 URL 的记录合并
2. 分类：根据能力标签归入预设分类（见下表）
3. 排序：同一分类内按名称字母序排列
4. 置信度标注：对自动识别的字段标注置信度

**步骤 4：生成输出**

根据 `output_format` 生成结果，并标注置信度：

- 高置信度（≥90%）：字段值直接从原文提取，无歧义
- 中置信度（70-89%）：字段值经推断得出，存在同义词或简写
- 低置信度（<70%）：字段值无法确定，需用户确认

**步骤 5：自查与交付**

- 检查字段完整性：每条记录是否包含名称、描述、分类
- 检查格式正确性：列对齐、JSON 语法有效

## 四、置信度门控：不编造原则

当信息不足以确定某个字段值时，采用以下策略：

| 场景 | 处理方式 |
|------|----------|
| 服务器名称缺失 | 输出 `[需核实:name]`，并提示用户补充 |
| 功能描述模糊 | 输出 `[需核实:capabilities]`，给出可能选项供用户选择 |
| 传输方式未知 | 输出 `[需核实:transport]`，不猜测默认值 |
| 依赖要求不明确 | 输出 `[需核实:dependencies]`，标注"未在原文中提及" |

**硬性规则**：

## 六、FAQ 反模式：常见坑与对照

### 反模式 1：过度推断

- **错误做法**：服务器描述为"提供数据库接口"，直接推断为"支持 MySQL 和 PostgreSQL"
- **正确做法**：标注为 `[需核实:数据库类型]`，提示用户确认具体支持的数据库

### 反模式 2：忽略版本信息

- **错误做法**：只提取服务器名称，忽略协议版本（如 MCP 协议 2025-03-26 版本）
- **正确做法**：单独列出 `protocol_version` 字段，未提及则标注"未指定"

### 反模式 3：混淆服务器与客户端

- **错误做法**：将 MCP 客户端（如 Claude Desktop）误认为服务器
- **正确做法**：仅处理明确标注为"server"或"服务器"的条目，存疑时向用户确认

### 反模式 4：重复记录未合并

- **错误做法**：同一服务器出现两次（一次全名、一次缩写），输出两条记录
- **正确做法**：按名称归一化规则合并，保留信息更完整的一条

### 反模式 5：忽略上下文依赖

- **错误做法**：服务器 A 依赖服务器 B 才能运行，但输出时未标注依赖关系
- **正确做法**：增加 `depends_on` 字段，明确标注服务器间的依赖关系
