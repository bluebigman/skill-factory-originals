## 三、标准流程

### 前置条件

| 条件项 | 要求 | 检查方式 |
|--------|------|----------|
| Python 版本 | ≥ 3.9 | `python --version` |

| 目标目录 | 存在且可写 | `ls -ld <目标目录>` |

### 执行步骤

#### 步骤 1：环境体检

运行以下命令收集环境信息：

```bash
gpt-engineer --selftest
gpt-engineer --version
python --version
echo "OPENAI_API_KEY=${OPENAI_API_KEY:+已设置}" 
echo "目标目录状态：$(ls -ld <目标目录> 2>&1)"
```

输出格式：

```
环境体检报告
├── Python 版本: 3.11.4 ✅
├── gpt-engineer: 0.3.2 ✅
├── OPENAI_API_KEY: 已设置 ✅
└── 目标目录: 可写 ✅
结论: 全部通过，可以开始
```

#### 步骤 2：需求描述质量评分

对用户输入的需求描述按以下维度评分：

| 评分维度 | 权重 | 评分标准 |
|----------|------|----------|
| 功能明确性 | 30% | 是否说清「做什么」 |
| 技术约束 | 20% | 是否指定语言、框架、接口 |
| 输入输出定义 | 20% | 是否说明输入格式与期望输出 |
| 边界条件 | 15% | 是否提到异常处理、性能要求 |
| 验收标准 | 15% | 是否定义「怎样算完成」 |

评分规则：
- 每个维度 0-10 分，加权求和后 × 10 得到百分制总分
- 总分 ≥ 85：可直接进入生成阶段
- 总分 60-84：建议补充需求后生成
- 总分 < 60：必须补充需求，否则生成结果大概率偏离预期

#### 步骤 3：逐维度改写建议

针对评分低于 7 分的维度，输出改写建议：

| 原描述（示例） | 问题 | 建议改写 |
|----------------|------|----------|
| "写个博客系统" | 功能不明确 | "写一个支持 Markdown 编辑、标签分类、全文搜索的博客系统，后端用 Python FastAPI，前端用 Vue 3，数据存 SQLite" |
| "要快" | 无量化标准 | "首页响应时间 < 500ms，支持 100 并发请求" |
| "处理用户输入" | 输入输出不清晰 | "接收 JSON 格式的 POST 请求，字段包括 username（字符串，3-20 字符）和 email（合法邮箱格式），返回 200 + 用户 ID 或 400 + 错误信息" |

#### 步骤 5：产物完整性审查

对 gpt-engineer 生成的工程执行三项检查：

| 检查项 | 判定标准 | 缺失处理 |

## 六、FAQ 反模式

### 常见坑 1：需求描述过于笼统

- **错误做法**："帮我写个工具"
- **正确做法**："写一个命令行工具，输入 CSV 文件路径，输出按指定列排序后的新 CSV 文件，支持升序/降序参数"
- **原因**：AI 无法从模糊描述推断具体功能，生成结果必然偏离预期

### 常见坑 2：跳过环境体检直接生成

- **错误做法**：直接运行 `gpt-engineer` 然后报错
- **正确做法**：先执行 `gpt-engineer --selftest` 确认环境就绪
- **原因**：环境问题（如密钥缺失）会导致生成中断，且错误信息不直观

### 常见坑 3：忽略凭据扫描

- **错误做法**：生成后直接提交到 Git 仓库
- **正确做法**：先执行凭据扫描，确认无敏感信息后再提交
- **原因**：AI 可能将示例密钥或硬编码凭据写入代码，直接提交会造成泄露

### 常见坑 4：把审查报告当逻辑正确性证明

- **错误做法**：审查通过 = 代码没问题
- **正确做法**：审查通过仅代表结构完整、无明文凭据，业务逻辑仍需人工验证
- **原因**：审查不涉及逻辑正确性，这是工具边界

### 常见坑 5：在超大仓库上运行扫描

- **错误做法**：对 5000+ 文件的仓库执行扫描
- **正确做法**：拆分模块或使用专业审计工具
- **原因**：扫描上限 2000 文件 / 512 KB 单文件，超出部分自动跳过，结果不完整
