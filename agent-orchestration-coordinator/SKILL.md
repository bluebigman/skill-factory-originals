## 三、标准流程：从输入到输出

### 3.1 前置条件

| 条件 | 要求 | 处理方式 |
|------|------|----------|
| 任务描述 | 清晰、具体，包含明确目标或交付物 | 不清晰时要求用户补充 |
| 外部数据需求 | 如有，需用户自行准备并提供 | 提示用户准备数据 |
| 子任务列表 | 可选，用户可直接提供 JSON 格式的子任务列表 | 跳过拆解步骤直接执行 |

### 3.2 执行步骤

**步骤 1：输入解析**
- 接收用户输入，判断是"一句话任务"还是"JSON 子任务列表"
- 若为 JSON 列表，校验格式完整性（每个子任务需含 `id`、`desc`、`role`、`depends` 字段）

**步骤 2：任务拆解**（仅针对一句话任务）
- 分析任务目标，识别关键维度
- 拆分为 3-8 个子任务，每个子任务包含：
  - `id`：唯一标识符（如 `task-001`）
  - `desc`：任务描述（一句话，明确交付物）
  - `role`：执行角色（如 `researcher`、`analyst`、`writer`）
  - `depends`：依赖项数组（可为空，引用其他子任务的 `id`）

**步骤 3：依赖排序**
- 构建依赖图，检查是否存在循环依赖
- 使用拓扑排序算法生成执行队列
- 标记可并行执行的子任务组

**步骤 4：角色分配与执行**
- 为每个子任务分配代理角色
- 按执行队列顺序执行，并行组同时推进
- 每个子任务执行时，明确输入、约束和预期输出

**步骤 5：结果汇总**
- 收集所有子任务输出
- 整合为结构化报告，包含：
  - 摘要：整体结论概述
  - 子任务详情：每个子任务的输入、输出、状态
  - 置信度：整体结果的可信度评估
  - 下一步建议：基于结果推荐的后续动作

### 3.3 输出规范

**输出格式**：JSON 或 Markdown（用户可选）

**JSON 输出示例**：
```json
{
  "summary": "已完成竞品调研，共分析 5 家主要竞品",
  "subtasks": [
    {
      "id": "task-001",
      "desc": "收集竞品 A 的产品信息",
      "role": "researcher",
      "status": "completed",
      "output": "竞品 A 的核心功能清单...",
      "confidence": 0.92
    }
  ],
  "overall_confidence": 0.87,
  "next_steps": ["深入分析竞品 B 的定价策略", "整理差异化优势对比表"]
}
```

**Markdown 输出示例**：
```markdown

|----|------|------|------|--------|
| task-001 | 收集竞品 A 的产品信息 | 研究员 | ✅ 完成 | 92% |

## 下一步建议
- 深入分析竞品 B 的定价策略
- 整理差异化优势对比表
```

## 四、置信度门控：不编造原则

### 4.1 置信度评估标准

| 置信度范围 | 等级 | 说明 |
|------------|------|------|
| 0.9 - 1.0 | 高 | 信息充分，来源明确，逻辑自洽 |
| 0.7 - 0.89 | 中 | 信息基本充分，部分推断成分 |
| 0.5 - 0.69 | 低 | 信息不足，存在推测或假设 |
| < 0.5 | 极低 | 信息严重不足，仅提供方向性建议 |

### 4.2 低置信度处理规则

- 当某个子任务的输出置信度低于 0.7 时，在该字段后标注 `[需核实:字段名]`
- 示例：`"market_size": "约 500 亿 [需核实:数据来源]"`
- 最终报告中，低置信度内容会以醒目方式标注，提醒用户谨慎采信
- 若整体置信度低于 0.6，报告开头会添加警示说明

### 4.3 信息不足时的行为

- 不猜测、不编造缺失信息
- 在报告中明确列出"信息缺口清单"
- 建议用户补充哪些数据或信息以提高置信度
