## 三、标准流程

### 3.1 前置条件

| 条件 | 要求 | 检查方式 |
|------|------|----------|
| 输入文件格式 | JSON / CSV / YAML | 文件扩展名校验 |
| 命名规范 | 文件需包含实体名（如 `user.json`） | 正则匹配 `^[a-z_]+\.(json\|csv\|yaml)$` |
| 目录结构 | 所有待处理文件在同一目录 | 目录存在性检查 |
| 字段完整性 | 每个记录至少包含 `id` 和 `name` 字段 | 字段缺失检测 |

### 3.2 执行步骤

1. **准备输入**
   - 将待处理文件放入同一目录（如 `./input/`）
   - 确认命名规范一致（小写 + 下划线，如 `user_profile.json`）
   - 检查文件编码为 UTF-8

2. **试运行**
   - 执行命令：`resource-controller --dry-run ./input/user.json`
   - 核对输出字段名、类型、嵌套层级
   - 确认控制器方法（GET/POST/PUT/DELETE）是否完整
   - 检查命名转换是否符合预期

3. **批量执行**
   - 确认试运行无误后，执行：`resource-controller ./input/`
   - 系统自动创建 `./backup/` 目录并复制原始文件
   - 输出目录为 `./output/`，每个文件对应一个控制器

4. **校验结果**
   - 抽查 3-5 个输出文件
   - 核对关键字段（`id`、`name`、`created_at`）与源数据一致
   - 验证控制器方法数量与源数据操作类型匹配

### 3.3 输出规范

| 输出项 | 格式 | 示例 |
|--------|------|------|
| 控制器文件 | `{Entity}Controller.{ext}` | `UserController.java` |
| 方法命名 | `{verb}{Entity}` | `getUser`、`createUser` |
| 字段映射 | 源字段 → 目标字段 | `user_name` → `userName` |
| 错误处理 | 统一返回 `{code, message, data}` | `{"code":404,"message":"Not Found","data":null}` |
