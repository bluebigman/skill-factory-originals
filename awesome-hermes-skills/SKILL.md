3. 如需按关键词筛选，在命令后追加关键词，如 `技能列表 文本处理`。系统返回所有名称、简介或标签中包含"文本处理"的技能。

#### 流程 B：获取装配建议

1. 用自然语言描述你的任务，例如："我需要从一份销售数据中提取趋势，并生成月度对比图"。

```

  子任务3: 生成月度对比图 → 需要可视化类技能
```

3. 返回装配方案，格式如下：

```

  步骤1: skill-data-reader    → 读取数据
  步骤2: skill-trend-analyzer → 提取趋势
  步骤3: skill-chart-builder  → 生成对比图
  衔接说明: 步骤2的输出（趋势指标）直接作为步骤3的输入参数
  预估耗时: 中等（取决于数据量）
```

4. 如需备选方案，输入 `备选方案` 获取对比：

```

  步骤1: skill-all-in-one      → 一步完成读取+分析
  步骤2: skill-chart-builder   → 生成对比图
  取舍点: 方案#2 更省步骤，但灵活性低于方案#1，适合数据格式规整的场景
```

1. 输入 `--selftest`。

```
  [通过] 依赖可用性 — 所有技能的前置依赖均已满足
  [通过] 输出格式正确性 — 目录与装配方案输出符合规范
```

- 目录清单：按分类分组，每个技能占一行，格式为 `技能ID | 技能名称 | 一句话简介`

## 六、FAQ 反模式

### 坑 1：把"技能列表"当成"技能执行"

- **反模式**：用户输入 `技能列表 数据清洗` 后，期待系统直接执行数据清洗。
- **正确理解**：`技能列表` 只做目录浏览和筛选，不执行任何技能。执行需要调用对应的下游技能。
- **建议**：先浏览目录找到目标技能，再直接调用该技能。

### 坑 2：任务描述过于笼统

- **反模式**：输入"帮我处理数据"——系统无法判断是清洗、分析、还是可视化。
- **正确理解**：装配建议依赖任务的可拆解性，描述越具体，方案越精准。
- **建议**：按"输入是什么 → 要做什么 → 输出什么"的结构描述任务。

### 坑 3：忽略衔接说明

- **反模式**：用户只看步骤列表，忽略步骤间的数据传递说明，导致实际执行时卡在接口对接。
- **正确理解**：装配方案中的"衔接说明"是方案可行性的关键，它标注了前一步输出如何作为后一步输入。
- **建议**：执行前通读衔接说明，确认数据格式兼容。

### 坑 4：遇到 `[需核实:...]` 占位符后强行继续

- **反模式**：系统标注信息不足，用户仍要求"先给个方案再说"。
- **正确理解**：占位符意味着该处信息缺失，强行生成方案会导致后续执行失败。
- **建议**：按占位符提示补充信息，或更换任务描述。

### 坑 5：只取一套方案，不做对比

- **反模式**：拿到推荐方案后直接执行，不查看备选方案。
- **正确理解**：推荐方案基于通用规则，备选方案可能更适合特定场景（如数据量小、格式规整）。
- **建议**：对同一任务请求多套方案，对比后选择最适合的。
