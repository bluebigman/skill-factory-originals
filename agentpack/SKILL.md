### 1.1 能做什么

| 能力项 | 说明 | 典型场景 |
|--------|------|----------|
| 关键词路由 | 根据任务描述中的具体关键词，将任务分发至最合适的处理模块 | "把销售数据按季度汇总并生成图表" → 数据分析模块 |
| 缓存管理 | 清理项目结构变化后遗留的缓存目录，强制触发重新分析 | 重构代码目录后，删除 `.cache/` 下的旧索引 |

| 批量任务串联 | 使用分号分隔多个子任务，一次调用完成多步操作 | `清理缓存; 重新分析; 生成报告` |

### 1.2 不能做什么

| 限制项 | 说明 |
|--------|------|
| 不执行模糊指令 | 任务描述缺少具体关键词时，拒绝路由并提示补充信息 |
| 不自动修改业务代码 | 仅负责任务调度与缓存管理，不涉及业务逻辑变更 |
| 不保证路由绝对正确 | 置信度低于 0.5 的结果必须人工复核，系统不承担误判责任 |
| 不处理跨项目依赖 | 仅针对当前项目上下文操作，不感知其他项目的缓存或结构 |

### 1.3 适用对象

- 使用命令行工具进行批量文件操作的开发者
- 需要频繁清理缓存并重新分析项目结构的团队

## 三、标准流程

### 3.1 前置条件

| 条件 | 检查方式 | 不满足时的处理 |
|------|----------|----------------|
| 项目目录存在 | `ls <project_dir>` | 报错 `E1001`，提示目录不存在 |
| 缓存目录可写 | `test -w <cache_dir>` | 报错 `E1002`，提示权限不足 |
| 任务描述非空 | 检查输入参数 | 报错 `E1003`，提示缺少任务描述 |
| 关键词可提取 | 正则匹配关键词库 | 报错 `E1004`，提示描述过于模糊 |

### 3.2 执行步骤

#### 步骤 1：解析输入参数

```
agentpack --selftest
agentpack --version
agentpack "清理缓存; 重新分析" --dry-run
```

参数表：

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `--selftest` | 布尔 | 否 | 运行自检，验证环境配置 |
| `--version` | 布尔 | 否 | 输出版本号 |
| `--dry-run` | 布尔 | 否 | 预览模式，不实际执行 |
| 任务描述 | 字符串 | 是（除上述参数外） | 用分号分隔多个子任务 |

#### 步骤 2：提取关键词并路由

- 对任务描述进行分词，匹配预置关键词库（如"清理"、"分析"、"批量"、"重命名"等）
- 每个关键词对应一个处理模块，路由结果包含模块 ID 和置信度
- 置信度计算规则：匹配关键词数量 / 描述总词数，乘以 0.8 基础系数

示例：

```
输入: "清理缓存并重新分析项目"
关键词: [清理, 缓存, 重新分析, 项目]
路由: [缓存管理模块(0.92), 分析模块(0.88)]
```

#### 步骤 3：执行任务（或预览）

- 非 dry-run 模式：按路由顺序执行各模块
- dry-run 模式：输出每个模块将要执行的操作清单，不实际执行

#### 步骤 4：输出结果

输出规范：

```
[AgentPack] 任务执行完成
- 路由模块: 2 个
- 执行操作: 5 项
- 置信度: 0.90
- 耗时: 1.2s
- 详情: 见 /tmp/agentpack_result.json
```

## 六、FAQ 反模式

### 6.1 常见坑与反模式对照

| 坑 | 反模式（错误做法） | 正模式（正确做法） |
|----|--------------------|--------------------|
| 描述过于笼统 | "帮我处理一下" | "清理缓存并重新分析项目结构" |
| 忽略缓存清理 | 项目结构变化后直接分析，结果陈旧 | 先执行 `清理缓存`，再执行 `重新分析` |
| 跳过 dry-run | 直接批量重命名，误操作后无法回滚 | 先 `--dry-run` 预览，确认后再执行 |
| 忽视低置信度 | 置信度 0.3 的结果直接采用 | 人工复核，补充关键词后重新路由 |
| 多次调用浪费 | 清理和报告分开两次调用 | 使用分号串联：`清理缓存; 生成报告` |

### 6.2 反模式示例
