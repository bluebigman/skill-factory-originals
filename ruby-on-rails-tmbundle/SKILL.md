# Rails 代码片段速查生成器（ruby-on-rails-tmbundle）

## 一、能力边界：一页纸速查卡

| 维度 | 说明 |
|------|------|
| **核心用途** | 将 Rails 开发中反复出现的代码模式（模型关联、控制器动作、路由配置、迁移模板等）转化为可复用的代码片段，减少重复键入。 |
| **输入要求** | 待处理的 Ruby/Rails 源文件或代码片段文本，需为 UTF-8 编码，单文件大小建议不超过 200KB。 |
| **输出产物** | 结构化代码片段清单，包含片段名称、触发关键字、作用域、代码体、描述等字段。 |
| **处理模式** | 支持单文件试运行与多文件批量处理两种模式。 |

### ✅ 能做

- 从 Rails 项目源文件中提取常见的代码模式（如 `has_many`、`belongs_to`、`validates`、`before_action` 等）。
- 将提取的模式转换为标准格式的代码片段（支持 TextMate/Sublime/VSCode 风格）。
- 对批量文件执行统一转换，并生成处理报告。
- 输出字段包含：片段名、触发词、作用域、代码体、说明、标签。

### ❌ 不能做

- 不能理解业务逻辑，无法判断代码片段的业务正确性。
- 不能自动执行 Rails 代码，仅做静态文本模式识别。
- 不能处理非 Ruby 语言文件（如 ERB 模板中的 HTML 部分需单独提取）。
- 不能保证提取的片段覆盖项目全部代码模式——仅识别规则库中定义的模式。

## 三、标准流程

### 前置条件

| 条件 | 要求 | 检查方式 |
|------|------|----------|
| 环境 | Ruby >= 2.7 或独立脚本环境 | `ruby -v` |
| 输入文件 | 待处理 `.rb` 文件，UTF-8 编码 | `file -i your_file.rb` |
| 目录结构 | 文件需在同一目录或明确指定路径 | 确认路径可访问 |
| 命名规范 | 文件名建议使用 snake_case（如 `user_model.rb`） | 目视检查 |

### 执行步骤

#### 第 1 步：准备输入

将待处理的 Ruby 文件放入同一目录，例如：

```
~/projects/my_rails_app/app/models/
├── user.rb
├── post.rb
└── comment.rb
```

确认文件命名符合 Rails 惯例（模型单数、控制器复数）。

#### 第 2 步：单样本试运行

先对单个文件执行提取，验证输出格式：

```bash
ruby on rails tmbundle --input ~/projects/my_rails_app/app/models/user.rb --output ./snippets/
```

检查输出目录中的 `user.sublime-snippet` 文件，核对以下字段：

| 字段 | 示例值 | 说明 |
|------|--------|------|
| `tabTrigger` | `has_many` | 编辑器中的触发词 |
| `scope` | `source.ruby` | 作用域（Ruby 文件） |
| `content` | `has_many :${1:comments}` | 代码体，`${1:...}` 为光标占位符 |
| `description` | `模型关联 - 一对多` | 片段说明 |

#### 第 3 步：批量执行

确认单文件输出无误后，对全量文件执行：

```bash
ruby on rails tmbundle --input ~/projects/my_rails_app/app/models/ --recursive --output ./snippets/
```

批量执行时自动执行以下操作：

1. 递归扫描目录下所有 `.rb` 文件
2. 对每个文件提取匹配的代码模式
3. 生成对应的 `.sublime-snippet` 文件
4. 生成 `processing_report.json` 处理报告
5. 原始文件不做任何修改（只读操作）

#### 第 4 步：校验结果

抽查输出条目，核对关键字段：

```bash
# 查看生成的文件列表
ls -la ./snippets/

# 抽查某个片段内容
cat ./snippets/user_has_many.sublime-snippet
```

核对要点：

- 片段名与源文件、代码模式对应
- `tabTrigger` 与代码模式关键字一致
- `content` 中的占位符编号连续（`${1:...}` → `${2:...}`）
- 无乱码、无缺失字段

### 输出规范

| 输出项 | 格式 | 示例 |
|--------|------|------|
| 片段文件 | XML 格式 `.sublime-snippet` | 见下方示例 |
| 处理报告 | JSON 格式 | `{"processed": 12, "extracted": 45, "failed": 1}` |
| 错误日志 | 文本格式 | `ERROR [user.rb:23] 无法识别的模式` |

**片段文件示例：**

```xml
<snippet>
  <content><![CDATA[has_many :${1:children}, dependent: :${2:destroy}]]></content>
  <tabTrigger>has_many</tabTrigger>
  <scope>source.ruby</scope>
  <description>模型关联 - 一对多（含级联删除）</description>
</snippet>
```

### 置信度分级

| 级别 | 判定标准 | 处理方式 |
|------|----------|----------|
| 高（≥90%） | 模式与规则库完全匹配，无歧义 | 直接生成片段 |

## 六、FAQ 反模式

### 常见坑与反模式对照

| # | 常见坑 | 反模式（错误做法） | 正确做法 |
|---|--------|-------------------|----------|
| 1 | **忽略试运行直接批量** | 直接对全量文件执行批量处理，结果输出大量错误片段 | 先对 1-2 个代表性文件试运行，确认输出格式和内容无误后再批量 |
| 2 | **过度依赖自动提取** | 认为提取的片段一定正确，不做任何人工校验 | 批量处理后至少抽查 20% 的片段，核对关键字段 |
| 3 | **修改原始文件** | 在提取过程中修改了源文件，导致代码丢失 | 本工具只读源文件，如需修改请先备份 |
| 4 | **忽略占位符提示** | 看到 `[需核实:...]` 直接删除，不补充实际值 | 将占位符替换为实际值后再使用片段 |
| 5 | **片段命名冲突** | 多个文件生成相同 `tabTrigger`，导致编辑器提示混乱 | 在片段名前加模块前缀，如 `user_has_many`、`post_has_many` |
| 6 | **不检查处理报告** | 批量处理后不查看 `processing_report.json`，遗漏失败文件 | 每次批量处理后必须查看报告，确认 `failed` 数量为 0 或已处理 |
