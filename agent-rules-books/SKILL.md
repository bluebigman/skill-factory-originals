## 六、FAQ 反模式

### 常见坑 1：过度依赖规则

| 反模式 | 正确做法 |
|--------|----------|
| 将本 Skill 输出的规则直接复制到生产环境，不做任何调整 | 将规则作为参考草案，根据团队实际情况调整后再应用 |
| 认为规则是"标准答案"，不质疑其适用性 | 理解规则背后的原理，判断是否适用于当前场景 |

### 常见坑 2：忽略上下文

| 反模式 | 正确做法 |
|--------|----------|
| 不提供技术栈、团队规模等上下文信息，期望得到精确答案 | 提供尽可能多的上下文信息，以获得更精准的规则匹配 |
| 将通用规则直接套用到特殊场景 | 识别场景特殊性，必要时标注 `[需核实:场景]` |

### 常见坑 3：混淆方法论边界

| 反模式 | 正确做法 |
|--------|----------|
| 将 Clean Code 的规则直接用于 DDD 的限界上下文划分 | 明确各方法论的适用范围，跨方法论使用时先进行冲突检测 |
| 认为 Refactoring 手法可以解决所有代码质量问题 | 理解重构只是质量改进的手段之一，还需配合测试、评审等 |

### 常见坑 4：忽视置信度标注

| 反模式 | 正确做法 |
|--------|----------|
| 忽略 `[需核实:xxx]` 标注，直接使用规则 | 对标注了需核实的规则，先查阅原始资料确认后再使用 |
| 认为置信度高的规则一定正确 | 置信度仅代表规则匹配的确定性，不代表规则本身的正确性 |

### 常见坑 5：批量处理时不做校验

| 反模式 | 正确做法 |
|--------|----------|
| 批量输入后直接使用全部输出，不做逐条校验 | 对批量输出逐条检查，确认每条规则都符合预期 |
| 批量处理失败后不查看错误码，直接重试 | 先查看错误码，根据错误码定位问题并修正 |

| 手法 | 适用场景 | 风险等级 | 置信度 |

### 示例 1：简单查询

**输入：** `"Clean Code 函数命名"`

**输出：**

```markdown
## 规则条目
- 方法论: Clean Code
- 主题: 函数命名

2. 避免使用模糊词汇（如 handle、process、do）
3. 命名应体现函数的目的，而非实现方式

### 示例

❌ 避免：`doStuff()`、`processData()`
```

### 示例 2：组合查询

**输入：** `"组合 DDD + Clean Code 输出规则文件"`

**输出：**

```markdown
## 组合规则草案（AGENTS.md 片段）

### 领域模型规则（DDD + Clean Code）
1. 聚合根命名使用领域术语，避免技术术语
2. 领域服务命名体现业务动作（如 `TransferMoneyService`）
3. 值对象实现为不可变类，命名使用描述性名词
4. 仓储接口命名使用 `Repository` 后缀

1. 函数保持单一职责，长度控制在 20 行以内
2. 使用异常处理错误，避免返回错误码
3. 注释解释业务意图，不重复代码逻辑

### 冲突提示
- DDD 强调聚合内高内聚，Clean Code 强调函数短小，两者在聚合方法设计上需平衡
- 建议：聚合方法可适当放宽长度限制，优先保证领域完整性
```
