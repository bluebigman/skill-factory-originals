## 三、标准执行流程

### 3.1 前置条件

| 条件 | 要求 | 检查方式 |
|------|------|----------|
| 任务描述 | 包含明确目标或交付物 | 用户输入中是否包含"做什么"和"产出什么" |

### 3.2 执行步骤

**Step 1：任务接收与澄清（输入阶段）**

接收用户的任务描述，检查是否满足以下条件：

- 目标是否明确（做什么）
- 交付物是否清晰（产出什么）
- 是否有隐含的约束条件（时间、格式、范围）

若信息不足，输出澄清问题清单：

```
[需核实:任务目标] 请说明您期望的最终交付物是什么？
[需核实:数据来源] 任务涉及的数据从何处获取？
[需核实:优先级] 哪些部分是必须完成的，哪些是可选的？
```

**Step 2：任务拆解（分解阶段）**

将任务拆解为子任务列表，每个子任务包含以下字段：

| 字段 | 类型 | 说明 | 示例 |
|------|------|------|------|
| `id` | string | 子任务唯一标识 | "task-001" |
| `desc` | string | 子任务描述 | "收集竞品A的产品功能列表" |
| `role` | string | 执行该任务的代理角色 | "研究员" |
| `depends` | array | 依赖的子任务ID列表 | ["task-000"] |

拆解原则：

- 每个子任务应能独立描述其输入和输出
- 子任务粒度适中（单个子任务不应过大或过小）
- 依赖关系明确（A 完成后才能执行 B）

**Step 3：依赖排序（排序阶段）**

对子任务进行拓扑排序，生成执行队列：

```
执行队列示例：
1. task-001 [研究员] 收集竞品A功能列表（无依赖）
2. task-002 [研究员] 收集竞品B功能列表（无依赖）
3. task-003 [分析师] 对比A/B功能差异（依赖: task-001, task-002）
4. task-004 [写手] 撰写竞品分析报告（依赖: task-003）
```

排序规则：

- 无依赖的任务排在最前，可标记为并行
- 有依赖的任务排在依赖任务之后
- 若存在循环依赖，输出错误提示

**Step 4：角色分配与执行（执行阶段）**

为每个子任务分配角色，角色类型包括：

| 角色 | 职责 | 适用场景 |
|------|------|----------|
| 研究员 | 信息收集与整理 | 数据采集、资料汇总 |
| 分析师 | 数据解读与洞察 | 趋势分析、对比评估 |
| 写手 | 内容生成与润色 | 报告撰写、文案创作 |
| 审查员 | 质量检查与修正 | 错误排查、一致性校验 |
| 协调员 | 汇总与整合 | 最终报告生成 |

执行时按执行队列顺序处理，每个子任务独立执行并记录结果。

**Step 5：结果汇总（输出阶段）**

将各子任务结果整合为最终报告，输出格式为 JSON：

```json
{
  "summary": "任务执行摘要",
  "subtasks": [
    {
      "id": "task-001",
      "desc": "子任务描述",
      "role": "执行角色",
      "status": "completed",
      "output": "子任务输出摘要",
      "confidence": 0.85
    }
  ],
  "overall_confidence": 0.82,
  "next_steps": ["建议的后续行动"]
}
```

### 3.3 输出规范

| 输出项 | 格式 | 说明 |
|--------|------|------|
| 子任务列表 | JSON 数组 | 包含 id、desc、role、depends 字段 |
