## 四、置信度门控

### 占位符机制

当智能体无法确定某个字段的正确值时，**不会猜测或编造**，而是输出 `[需核实:字段名]` 占位符。

| 场景 | 输出示例 | 处理方式 |
|------|----------|----------|
| 字段值缺失 | `[需核实:diagnosis_code]` | 人工查阅原始记录补充 |
| 字段值冲突 | `[需核实:patient_dob]` | 人工确认正确的出生日期 |
| 字段格式异常 | `[需核实:zip_code]` | 人工核对邮编格式 |
| 专科无法识别 | `[需核实:specialty]` | 人工判断所属专科 |

### 置信度等级

| 等级 | 标识 | 含义 | 处理建议 |
|------|------|------|----------|
| 高 | `confidence: 0.9-1.0` | 字段值确定 | 直接使用 |
| 中 | `confidence: 0.7-0.89` | 字段值较确定 | 抽查确认 |
| 低 | `confidence: 0.5-0.69` | 字段值不确定 | 人工复核 |
| 需核实 | `resolution: "needs_review"` | 无法确定 | 必须人工处理 |

### 门控规则

1. 置信度 < 0.7 时，自动标记为 `needs_review`
2. 字段值冲突时，优先标记占位符，不擅自选择
3. 占位符不参与后续计算，避免错误传播

## 六、FAQ 反模式

### 常见坑 1：忽略 `needs_review` 记录

**反模式**：直接使用输出 CSV，不检查 `processing_log.json` 中的 `needs_review` 记录。

**正确做法**：每次处理完成后，先筛选 `needs_review` 记录，人工确认后再使用数据。

```bash
# 正确做法
cat processing_log.json | jq '.records[] | select(.resolution == "needs_review")'
```

### 常见坑 2：修改输入文件后不重新处理

**反模式**：手动修改了 `./medical_input/` 中的原始文件，但未重新运行处理脚本。

**正确做法**：任何输入文件的修改，都必须重新运行 `run_agents.py` 生成新的输出。

### 常见坑 3：不检查字段映射结果

**反模式**：认为所有字段都自动映射正确，不抽查输出文件的字段值。

**正确做法**：随机抽取 5-10 条记录，比对原始数据和输出数据的字段值。

### 常见坑 4：忽略置信度门控

**反模式**：看到 `confidence: 0.6` 的记录，直接使用该值而不复核。

**正确做法**：置信度 < 0.7 的记录必须人工复核，确认后再使用。

### 常见坑 5：在未脱敏数据上运行

**反模式**：直接使用包含姓名、身份证号等 PHI 的原始数据运行工具。

**正确做法**：先对数据进行脱敏处理，确保符合 HIPAA 合规要求。
